- Phase 2A adaptive assembly lives in `_shared/narrative/adaptiveContext.ts` as an opt-in pure candidate-to-context function; keep live generation unchanged until controlled integration because context selection needs independent benchmarking and identity validation.
- Phase 2B identity integrity lives in `_shared/narrative/identity.ts` as pure functions (resolve, classify, gate, versioned commit/undo); not wired to live generation until 2D — no proposed entity gets an id or becomes canon without evidence and an explicit commit.
- Identity commits persist only through the `commit_identity_batch` database function (server-only, one transaction, idempotent on book+section+content hash+purpose+schema version, rejects authority inversion) — partial batches and retry duplicates are impossible at the database level, not just in tests.
- Phase 2D A/B switch: `books.controls.context_engine` ("adaptive" opts in; anything else = legacy, read server-side) selects the context path in `generate-content` via `_shared/narrative/adaptiveCandidates.ts`; adaptive fails open to legacy, and every section logs to `context_engine_runs` — legacy stays unchanged so the two can be compared fairly.
- Identity sync runs in `extract-narrative-state` after a completed extraction (accepted text only) via pure `_shared/narrative/identitySync.ts` + `identityRepo.ts`: only NEW_ENTITY or a single confident link gets an id, lower authority never overwrites higher, attributes commit through `commit_identity_batch`, and a rewritten section's older generated versions are removed — uncertain names are skipped, never guessed.
- Replaced technical artifacts are read from artifact descriptions by pure `_shared/narrative/deprecations.ts`: adaptive context shows a `[REPLACED — DO NOT USE: …]` tag beside the active API, and `check-continuity` deterministically flags reuse of the legacy name — the fix is enforced, not prompt-only.
- Person names with ≥2 tokens and different surnames resolve as separate entities; a shared given name is not duplicate evidence, and any later same-person claim goes to review (`reviewMerge`), never auto-merge.
- The browser sends a one-chapter outline slice with `chapterIndex: 0`; story-memory position comes from `absoluteChapterIndex` (server falls back to `chapterIndex` for old clients) — otherwise every section reads memory as if it were chapter 1.
- Benchmarks and live tests run on the book's own writer profile with the user's provider keys (production models), never on the built-in gateway defaults.
- `generate-content` accepts `dryRun: true` to return the assembled prompts with no AI call, charge or write — used to verify deployed context before any paid benchmark.
- Persona Studio Phase 1: every character level (seed → independent persona) hangs off one stable `narrative_identities.id`; a `personas` profile attaches 1:1 to that id, so promotion never rewrites relationships, appearances or canon. Pen names (`author_identities`), fictional identities and AI writer profiles stay separate entity kinds.
- Relationships (`narrative_relationships`) link identities of any level; DB triggers enforce same owner and same universe, and an identity with relationships cannot change universe — universes never mix silently.
- Chronology lives in pure `chronology.ts`: dates are `ApproximateDate` JSON resolved to day-level intervals; ages use exact month/day when both dates are exact, otherwise bounded ranges — only demonstrable conflicts are violations, overlaps are review, nothing is fabricated.
- Event time, learning time (`knowledge_acquisitions`) and reader disclosure are separate; narrator access uses learning time, never event time. Immediate narration sees only what was known at the scene; retrospective narration keeps scene perception bounded but may use hindsight learned by the telling point.
- Universe-scoped canon (`canonical_facts.universe_id`) can be set only by the server, only to the book's own universe, and only on ESTABLISHED (accepted + extracted) facts — plans never become universe history. `books.narrative_vantage` (default immediate) is locked by trigger once the book has words.
- Persona Studio (Phase 2): narrative identities, personas and relationships are created only by the `persona-studio` function (browser INSERT revoked) so identity resolution in pure `_shared/narrative/identityResolution.ts` is authoritative — any same-universe name/alias match needs an explicit author decision, never an auto-merge.
- Persona domain (`personas.category`, enduring expertise) is separate from per-book narrative role (`book_identity_roles`); AI Generate/Hybrid share one contract in `_shared/narrative/personaGeneration.ts` (prompt, parser, author-fact protection) and use the mock model unless `PERSONA_AI_ENGINE=live`.
- Multiple viewpoints may share a chapter; head-hopping is two viewpoints in the same section (`sections` "ch:sec" keys) — a shared chapter is advisory only.
- A character can join a book only if it belongs to the same story world (`book_identity_roles` trigger `enforce_book_role_universe`) — cross-world canon leaks are impossible at the database level.
- Covers, illustrations and portraits go through `_shared/ai/openaiImage.ts`: the user's saved OpenAI key first, the in-app OpenAI image model as fallback — one place to change image models.
- Planned cast is gated by debut in pure `cast.ts` (explicit `firstAppearance`, else first outline section naming them by full name or a cast-unique name token); both Standard and Adaptive include outline characters before extraction but withhold later debuts — outline canon is preserved without becoming present-scene knowledge.
- Planned cast members always get a book-scoped knowledge identity (`castIdentities.ts` + `ensureCastIdentities`) before knowledge sync, and pending `no_identity` reviews that now match are auto-resolved — a planned character must never reach "Characters to confirm"; only genuinely unplanned names do.
- Paragraph time anchors live in pure `temporalFrames.ts`: each accepted paragraph carries one anchor (relative phrase vs raw/exact stamp, verbatim; non-linear scenes open named frames with their own clocks) and `parseSectionMemory` re-derives the arithmetic deterministically — a demonstrably impossible timeline fails extraction, never the accepted prose.
- Planning rules (Phases C–I, blueprints, validation) live in `planning/AGENTS.md`, and `plan-book` rules (book setup, knowledge sync, test mode) live in `supabase/functions/plan-book/AGENTS.md` — read them before changing files there.
