- Phase C progressive planning lives in pure `_shared/narrative/planning/engine.ts` (master→chapter→section→beat skeleton, exact word allocation, dependency validation, downstream blast radius, reveal visibility) with nine adapters in `planning/adapters.ts` mapping all 22 book types; nonfiction adapters cannot hold reveals, and nothing is wired to generation until Phase D so live writing stays unchanged.
- Only PENDING, non-`selftest_*` CRITICAL/MAJOR reconciliation logs may block generation (`planning/reconciliationFilter.ts`) — permanent Phase B self-test records must never block benchmarks.
- Phase D AI planning lives in pure `planning/aiPlanning.ts` (prompts, parsers, bounded repair ≤2, checkpointed chapter batch) behind owner-only `plan-book`; planners get the whole book incl. ending and all reveals, only prose roles get `proseWriterPlanView` — saves go through `save_master_plan_draft` / `save_progressive_plan_batch` (server-only, idempotent, versioned) and approval through `approve_master_plan` / `approve_progressive_plans` (signed-in owner, old approved version retired untouched). Not wired to prose generation until Phase E.
- Biography/memoir use the `narrative_nonfiction` adapter: scenes allowed, every planned claim carries an evidence tier, "documented" needs a provided source — nothing is invented or claimed verified.
- Phase E planning-aware context lives in pure `planning/planningContext.ts`: only an APPROVED, schema-compatible master (READY section plans override the skeleton) adds chapter/section/beat goals, spoiler-safe direction and active latest-version exact anchors to the Adaptive candidates; synopsis, ending, planner-only genre fields, later chapter goals and future reveal text (from any source) are filtered out, and any unusable plan yields the unchanged Adaptive build. Not wired to live generation until Phase F with Phase B safeguards.
- Phase F progressive pipeline is opt-in per book (`books.controls.planning_pipeline = "progressive"`, pure `planning/pipeline.ts` + `pipelineRepo.ts`): gate (previous section accepted + extracted, no undecided serious contradiction) → lease → plan-aware context in both modes → `commit_fenced_section` (fence + manuscript + acceptance + release in one transaction, accepted prose protected unless `replaceAccepted`) → `check-continuity` exact-anchor repair (≤2, required anchors only) and contradiction records → extraction promotes to ESTABLISHED via `mark_section_extraction`. Books without the flag run the unchanged path.
- Writers receive reveal `setupDirectives` (concrete on-page behaviour + viewpoint/reader layers), never the reveal summary or `secretTerms`; a directive that would leak is dropped and replaced by the generic setup line.
- Phase F safeguards: progressive writing holds a short lease renewed by a heartbeat (`createLeaseHeartbeat`) and a lost worker never commits; continuity revisions on progressive books save only via `commit_fenced_revision` (fence + text + acceptance hash in one transaction); progressive mode stops with `PLAN_REQUIRED` instead of writing without an approved plan; extraction failures mark memory sync FAILED (accepted prose untouched) and keep blocking the next section until a retry succeeds.
- Phase G unified validation lives in pure `planning/validation.ts`: vocabulary bans come only from book/genre/author settings (none by default), repetition is contextual (dialogue, declared motifs/terminology, children's/poetry exempt), deferred setups are not omissions, only material fact/identity/timeline/canon findings go to `canon_reconciliation_logs` while everything else goes to `editorial_validation_findings` (owners may change only status/notes), the revision-change ratio (`controls.revisionWarnRatio`, default 0.2) is a warning that routes to author approval, and the free deterministic pass runs before `commit_fenced_section` — a material finding means the draft is not accepted and prior accepted prose is untouched; automatic repairs never overwrite prose already extracted into story memory.
- Phase G runtime gate lives in pure `planning/evaluator.ts` (+ `evalContext.ts`, I/O in `preAcceptanceServer.ts`): Stage 1 free checks plus ONE combined evaluator call (role `continuity_checker`) per validation, ≤2 targeted find/replace repairs (`continuity_reviser`) with full revalidation; writing quality is capped below material, and an evaluator failure holds the draft — critical checks are never skipped to save cost.
- Drafts that fail validation become `book_candidate_drafts` (owner read-only; writes only via `save_candidate_draft` / `commit_candidate_draft` / `discard_candidate_draft` behind the owner-only `candidate-review` function) — accepting a held draft re-runs full validation and requires every linked contradiction decided.
- "Adopt the change" decisions are `PENDING_APPLICATION` until `commit_candidate_draft` moves them to `AWAITING_SYNC` in the acceptance transaction and extraction (`finalize_canon_application`) marks them `APPLIED`; a failed or discarded acceptance leaves prior canon authoritative.
- Replacing an accepted section flags memory from that section (SUPERSEDED) and later (UNCERTAIN) across facts, states, events, timeline, threads, entities, identity versions and anchors inside `commit_fenced_section`; context loaders read only `canon_status = ESTABLISHED`, and nothing is deleted.
- Progressive books keep only server-accepted text in the outline (`write_accepted_outline_text`, hash-checked); the browser waits for the section verdict and pauses on a held draft.
- Phase I: Stage 5 writing quality uses a per-adapter rubric (`QUALITY_RUBRICS` in `planning/evaluator.ts`), advisory only until calibrated against human editors; progressive prompts enforce only author-configured word bans; the browser checks a section's prior server outcome before writing and pauses (never regenerates) when validation is still running.
- Progressive books get a closed-world writing rule (no invented named people, places or plot facts) and "planned character entrance" hooks; Standard prompts stay byte-identical.
- Stage 2 chapter blueprints live in pure `planning/blueprint.ts` and are stored as progressive plan level `BLUEPRINT` (chapter-scoped, PLANNED until the author approves it individually; bulk approval skips it): synopsis has no word limit, cast/locations/events have stable ids, microbeats must cover every section in order and reference only known ids, events cite their approved source, new people only via `castProposals`, and later reveal secrets may appear only in the author layer. Not used by prose generation until Stage 3.
- Detailed blueprints are required only when `books.controls.blueprint_mode = "required"` on a progressive book (set when Progressive is first turned on; older progressive books opt in explicitly); a blueprint is approved alone, never while a castProposal is unregistered in `story_characters`, and `generate-content` refuses to write a chapter without an approved blueprint — listing a person never authorizes them.
